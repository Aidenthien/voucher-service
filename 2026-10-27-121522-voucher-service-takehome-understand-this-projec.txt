  1. Tech stack

  - Java 17, Spring Boot 3.2.5, Gradle. See build.gradle
    (voucher-service/build.gradle).
  - Spring Web for the REST controllers, Spring Data JPA with Hibernate for
    persistence, and the H2 in-memory DB.
  - spring-boot-starter-validation is a dependency, but nothing uses it.
  - application.yml (voucher-service/src/main/resources/application.yml) sets
    ddl-auto: none and sql.init.mode: always. Hibernate never generates tables.

    and recreates everything on each boot, then data.sql

    Liquibase.

  3. Coding patterns (match these when you add code)

  - Errors come back as values, not exceptions. A service returns
    RedeemResponse.fail("reason") and the HTTP status is always 200, so callers
    have to check result. There's no @ControllerAdvice. A new "limit exceeded"
    rejection fits as one more RedeemResponse.fail(...).
  - Statuses are strings ("ACTIVE", "REDEEMED", "VOID"), not an enum.
  - Mixed dependency injection. VoucherController and VoucherService use field
    @Autowired; CampaignController and CampaignStatsService use constructor
    injection. You can see where different people have worked on it.
  - Entities and DTOs are hand-written POJOs with getters and setters (no
    Lombok, no records), and they use java.util.Date.
  - There's no @Transactional anywhere.
  - Repository lookups use Spring Data's derived query methods (method names
    like findByCode); there's no custom SQL.

  4. End-to-end flow: POST /vouchers/RAYA-0001/redeem?userId=user-1

  The other endpoints are simpler:
  - Void: finds the voucher by code, sets status to VOID, saves and returns OK.
    It doesn't check the current status, doesn't restore stock and doesn't touch
    the redemption rows.
  - Stats: loads the campaign, then runs one redemption query per voucher (an
    N+1 pattern). It counts a voucher as "redeemed" if it has any redemption
    row, and as "active" if its status is ACTIVE.

  5. Where the limit belongs

  The rule goes between steps 6 and 7 of VoucherService.redeem(). It needs four
  things:
  - A campaign column, for example max_redemptions_per_user INT NOT NULL DEFAULT
    2, in schema.sql, plus a matching field on Campaign.
  - A count query, for example
    RedemptionRepository.countByCampaignIdAndUserId(...).
  - A check that rejects the redemption once the count reaches the limit.
  - A RedeemResponse.fail(...) with a clear message.

  The trap in the seed data

  user-99 has two redemption rows on campaign 1, but one of those vouchers
  (RAYA-0005) is now VOID.
  - If voided redemptions count, user-99 is already at the default limit of 2.
  - If they don't, user-99 can redeem one more.

  You need to decide this deliberately and write it down in NOTES.md. redemption
  has no status column, so excluding voided ones means joining to voucher or
  adding a status.
